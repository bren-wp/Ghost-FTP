# Ghost FTP privacy

Ghost FTP **0.0.4** is designed to operate without application telemetry, advertising, behavioral analytics, fingerprinting, hidden crash upload or a mandatory Ghost FTP account.

## Data Ghost FTP does not intentionally collect

Ghost FTP does not include a product service that receives:

- usage analytics;
- advertising identifiers;
- filenames for analytics;
- saved server profiles for synchronization;
- connection history for marketing;
- passwords or private-key passphrases;
- machine inventory for a Ghost FTP account.

Production CI and release workflows explicitly execute `go telemetry off` and verify that Go telemetry remains disabled.

## Normal network activity

Network traffic is generated by user-directed FTP, FTPS or SFTP actions against the server the user selected. Keepalive, listing, diagnostics and transfer metadata are part of that server interaction, not a Ghost FTP telemetry channel.

Fresh desktop quick-connect defaults use FTPS; plain FTP remains an explicit unencrypted compatibility choice. Ghost FTP does not silently downgrade a failed secure FTPS request to FTP and does not silently download protocol runtimes or networking SDKs while running.

The Android development client follows the same privacy model: user-directed server traffic is not proxied through a Ghost FTP product backend, and local document access uses Android platform document capabilities rather than a hidden sync service.

## Connection diagnostics

Connection failures are converted into privacy-safe categories and remediation text. The diagnostic layer is tested so user-facing errors do not intentionally reproduce passwords, passphrases or protected profile payloads.

Raw `curl`, `sftp` and related child-process diagnostics are reduced to a stable semantic category and a conservative retry decision while the bounded process output is still in scope. The retained `toolError` contains only the normalized tool identifier, exit code, semantic category and retry flag; it does not retain the raw diagnostic string for later parsing. This shortens the in-memory lifetime of hostnames, usernames, remote paths or private-key paths that a system networking tool may have emitted.

SFTP host-key discovery follows the same boundary: raw `ssh-keyscan` stderr is used only for transient local error classification and is not reproduced verbatim in the user-facing failure string or retained inside the resulting tool error. Hostnames, local paths and other tool-emitted details therefore do not need to be echoed merely to explain a failed fingerprint scan.

When reporting a problem, users should still remove real hostnames or paths if those details are confidential.

## Saved profiles

Profiles are local. Saving a site does not create a cloud record.

Credential persistence is opt-in:

- Windows uses the current-user operating-system protection boundary;
- Linux uses local authenticated encryption with user-private key material.

Ghost FTP 0.0.4 applies explicit credential-save consent to the maintained Windows and Linux profile-save flows. Declining consent can still save non-secret profile fields without turning newly entered password/passphrase values into durable state. Profile identity binding prevents protected credentials from silently migrating to a changed endpoint/account/private-key identity.

A protected secret is not meant to become plaintext JSON merely because decryption failed. The safe fallback is to request the secret again.

## Session-only secrets

Quick/ad-hoc connection credentials can remain runtime-only. Passwords and key passphrases should not be written to disk unless the user chooses the saved-credential option and the platform protection path succeeds.

On Linux, process-local protected-secret handles distinguish session-owned and borrowed profile-owned secrets. Session-owned handles are forgotten promptly on close or failed/abandoned SFTP setup; borrowed profile secrets are not invalidated merely because a connection session ends.

## Navigation metadata

Bookmarks and profile start-directory state are local navigation metadata, not credential stores. Remote bookmark/start-directory activation is account/session bound before it becomes authoritative, so saved navigation state cannot silently become authority for a different server identity.

## Settings

Language, appearance, transfer preferences, recent local state and other desktop settings are stored locally. Settings recovery uses local backup/replacement behavior and does not contact an external Ghost FTP product service.

Classic Light is the fresh/fallback appearance. Selecting Dark is an explicit local preference on the maintained native desktop frontends and does not load remote themes, fonts or style services.

## Transfer data

Ghost FTP necessarily reads local files selected for upload and writes files selected for download. Transfer content is sent only to/from the selected server through the chosen protocol.

Staging, rollback and source-snapshot files are local operational state. They are not uploaded to a Ghost FTP product service. Incomplete/cancelled staged downloads must not be promoted to a final user-visible object merely to simplify cleanup.

## GitHub Release and Packages privacy

Official public release artifacts are built in GitHub Actions from repository source. The public release allow-list includes only Windows/Linux product binaries/packages plus generated verification files.

The current GitHub Package (`ghcr.io/bren-wp/ghost-ftp`) is built from the verified release directory only. The OCI bundle does not intentionally contain saved profiles, user files, local application data, signing private keys or CI secrets. Docker networking is disabled during the bundle build.

The Android development APK is a separate CI artifact and is not silently inserted into the public Windows/Linux release bundle.

## Signing secrets

Production Authenticode credentials are expected to exist only as protected GitHub Actions secrets. Temporary PFX material is written into the runner temporary directory for signing and removed after use. Private signing material must never be committed to the repository or included in release/package files.

## Documentation and screenshots

Authentic UI evidence is captured from real Windows, Linux and Android runtime surfaces by the dedicated read-only CI workflow. The workflow must not commit or push screenshot evidence back into the source branch it is validating.

The exact-head evidence bundle contains 15 runtime images: five Windows, three Linux and seven Android. `scripts/assemble_ui_evidence.py` verifies source SHA, workflow-run identity, expected filenames, byte counts and SHA-256 values before the bundle is accepted.

Screenshots and fixtures must contain only synthetic/non-sensitive values and must not expose real customer hosts, usernames, credentials or local private paths. Mockups or generated approximations are not substitutes for authentic runtime evidence.

Documentation media is repository-local. The active README/documentation surface does not intentionally embed remote badge images, tracking pixels, analytics images, remote icon resources, remote webfonts or other externally hosted media that would cause a network request merely because documentation is rendered. Ordinary text hyperlinks may still point to the official product, GitHub release/package pages and other documented destinations; they are not fetched by Ghost FTP at runtime.

The canonical documentation logo is `build/icon.png`. The maintained checked-in desktop visual set includes `docs/images/ghost-ftp-main-workspace.png`, `docs/images/ghost-ftp-site-manager.png`, `docs/images/ghost-ftp-settings.png` and `docs/images/ghost-ftp-about.png`; release-prep runtime evidence is additionally published as immutable workflow artifacts rather than self-committed source changes.

## Logs and support

Ghost FTP aims to make operational logs useful without exposing credentials. Users should not paste real passwords, private keys, passphrases or confidential server content into public support requests.

## Third-party servers and tools

A server chosen by the user can observe the protocol traffic necessary for that connection and is governed by the server operator's own policy. System FTP/SFTP tools invoked by Ghost FTP operate under the local operating system and their own implementation behavior.

## No sale of user data

Ghost FTP contains no advertising data broker integration and no product backend designed to sell application usage/profile data.
