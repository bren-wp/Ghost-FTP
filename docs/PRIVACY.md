# Ghost FTP privacy

Ghost FTP **1.0.0 Stable** is designed to operate without application telemetry, advertising, behavioral analytics, fingerprinting, hidden crash upload or a mandatory Ghost FTP account.

## Data Ghost FTP does not intentionally collect

Ghost FTP does not include a product service that receives:

- usage analytics;
- advertising identifiers;
- filenames for analytics;
- saved server profiles for synchronization;
- connection history for marketing;
- passwords or private-key passphrases;
- machine inventory for a Ghost FTP account.

Production CI and release workflows execute `go telemetry off` and verify that Go telemetry remains disabled.

## Normal network activity

Network traffic is generated by user-directed FTP, FTPS or SFTP actions against the server the user selected. Keepalive, listing, diagnostics and transfer metadata are part of that server interaction, not a Ghost FTP telemetry channel.

Ghost FTP does not silently download protocol runtimes or networking SDKs while the desktop application is running.

## Connection diagnostics

Connection failures are converted into privacy-safe categories and remediation text. The diagnostic layer is tested so user-facing errors do not intentionally reproduce passwords, passphrases, protected profile payloads, private-key paths or raw child-process output.

When reporting a problem, users should still remove confidential hostnames/paths or server content from screenshots/logs.

## Saved profiles

Profiles are local. Saving a site does not create a Ghost FTP cloud record.

Credential persistence is opt-in:

- Windows uses the current-user operating-system protection boundary;
- Linux uses local authenticated encryption with user-private key material.

A protected secret is not converted to plaintext storage merely because decryption failed. The safe fallback is to request the secret again.

## Session-only secrets

Quick/ad-hoc connection credentials can remain runtime-only. Passwords and key passphrases should not be written to disk unless the user chooses saved credentials and the platform protection path succeeds.

## Settings

Language, theme, transfer preferences, recent local state and other desktop settings are stored locally. Settings recovery uses local backup/replacement behavior and does not contact BRENDIGO LTD.

## Transfer data

Ghost FTP necessarily reads local files selected for upload and writes files selected for download. Transfer content is sent only to/from the selected server through the chosen protocol.

Staging, rollback and source-snapshot files are local operational state. They are not uploaded to a Ghost FTP analytics/product backend.

## Official Release privacy

The GitHub Release is assembled from an explicit allow-list: verified Windows/Linux application packages plus `RELEASE-NOTES.txt`, `BUILD-METADATA.txt` and `SHA256.txt`.

The Release must not include saved profiles, runtime credentials, private signing material, user files, local application data, build caches or developer worktrees.

## GitHub Packages privacy

`ghcr.io/bren-wp/ghost-ftp` is built only after the GitHub Release has been verified. It is a non-runtime OCI distribution bundle containing `/ghostftp-release/` only.

The package build uses `FROM scratch` and Docker build networking is disabled. Registry authentication uses the short-lived Actions token through `--password-stdin` and a temporary `DOCKER_CONFIG` directory that is removed after use.

After publication the workflow pulls the package back from GHCR and compares embedded `SHA256.txt`/`BUILD-METADATA.txt`; package credentials are not copied into the bundle filesystem.

## Signing secrets and signing status

Production Authenticode credentials, when configured, exist only as protected GitHub Actions secrets. Temporary PFX material is written to the runner temporary directory and removed after use. Private signing material must never be committed or included in Release/Package files.

When no production certificate is configured, the release records `WINDOWS_AUTHENTICODE=unsigned`; it does not create a fake/self-signed publisher identity to hide the absence of a real certificate.

## Logs and support

Ghost FTP aims to make operational errors useful without exposing credentials. Do not paste real passwords, private keys, passphrases, confidential server data or signing secrets into public support requests.

## Third-party servers and system tools

A server selected by the user can observe protocol traffic necessary for that connection and is governed by its operator's policy. System `curl`/OpenSSH tools invoked by Ghost FTP operate under the local operating system and their own implementation behavior.

GitHub receives normal repository/Release/Packages traffic when maintainers publish software through GitHub Actions. That build/distribution traffic is separate from the Ghost FTP desktop runtime and is not application telemetry.

## No sale of user data

Ghost FTP contains no advertising data-broker integration and no product backend designed to sell application usage/profile data.
