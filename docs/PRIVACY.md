# Ghost FTP privacy

Ghost FTP **0.0.5** is designed to operate without application telemetry, advertising, behavioral analytics, fingerprinting, hidden crash upload or a mandatory Ghost FTP account.

The current public release platforms are Windows and Linux. Android and macOS are active native development/source surfaces with separate build and distribution boundaries. The browser connection helper is an optional local parsing/copy source surface. None of these surfaces introduces a Ghost FTP cloud relay or product analytics backend.

## Data Ghost FTP does not intentionally collect

Ghost FTP does not include a product service that receives:

- usage analytics;
- advertising identifiers;
- filenames for analytics;
- saved server profiles for synchronization;
- connection history for marketing;
- passwords or private-key passphrases;
- machine inventory for a Ghost FTP account;
- browser history or ordinary tab contents.

Production CI and release workflows explicitly execute `go telemetry off` and verify that Go telemetry remains disabled.

## Normal network activity

Network traffic is generated by user-directed FTP, FTPS or SFTP actions against the server the user selected on platforms where that protocol is maintained. Keepalive, listing, diagnostics and transfer metadata are part of that server interaction, not a Ghost FTP telemetry channel.

Fresh desktop quick-connect defaults use FTPS. Plain FTP remains an explicit unencrypted compatibility choice. Ghost FTP does not silently downgrade a failed secure FTPS request to FTP and does not silently download protocol runtimes or networking SDKs while running.

The Android development client follows the same privacy model: user-directed FTP/FTPS traffic is not proxied through a Ghost FTP product backend, and local document access uses Android Storage Access Framework capabilities rather than a hidden synchronization service. Android SFTP remains intentionally unavailable until strict native host-key identity verification has a maintained implementation.

The macOS development client uses the shared engine and native platform facilities. It does not add a Ghost FTP telemetry service, browser IPC bridge or localhost application server. Public macOS distribution remains a separate signing/notarization decision and does not change the runtime privacy contract.

## Browser connection helper

The optional `ekstenzije/` helper parses explicitly entered or pasted `ftp://`, `ftps://` and `sftp://` targets locally and can expose a safe target for explicit copy.

Its maintained privacy boundary is deliberately narrow:

- no FTP credential persistence;
- no ordinary-tab scraping;
- no broad host permission requirement;
- no remote executable code;
- no analytics or tracking endpoint;
- no supported browser-to-desktop launch/handoff contract today.

The helper is not a proxy and does not become a product backend for FTP-family traffic.

## Connection diagnostics

Connection failures are converted into privacy-safe categories and remediation text. The diagnostic layer is tested so user-facing errors do not intentionally reproduce passwords, passphrases or protected profile payloads.

Raw `curl`, `sftp` and related child-process diagnostics are reduced to a stable semantic category and conservative retry decision while bounded process output is still in scope. Retained tool errors carry only normalized identifiers/state needed by the application rather than preserving raw diagnostic text for later presentation. This reduces the in-memory lifetime of hostnames, usernames, remote paths or private-key paths a system tool may have emitted.

SFTP host-key discovery follows the same boundary: raw `ssh-keyscan` stderr is used only for transient local classification and is not reproduced verbatim in user-facing failures or retained as long-lived application state.

Android FTP authentication has an additional privacy boundary: server-controlled `USER`/`PASS` failure text is not exposed verbatim through user-facing exceptions, preventing a malicious or misconfigured server from reflecting a submitted password back into the UI.

When reporting a problem, users should still remove real hostnames, usernames and paths when those details are confidential.

## Saved profiles and protected credentials

Profiles are local. Saving a site does not create a Ghost FTP cloud record.

Credential persistence is opt-in and platform-local:

- Windows uses the current-user operating-system protection boundary;
- Linux uses maintained local authenticated-encryption/protected-secret handling;
- macOS development profiles use native Keychain-backed protection through the maintained platform bridge;
- Android saved-site state is intentionally non-secret in the current development client.

Ghost FTP 0.0.5 keeps credential-save consent separate from non-secret profile persistence. Declining consent can still save non-secret fields without silently turning newly entered passwords or passphrases into durable state. Profile identity binding prevents protected credentials from silently migrating to a changed endpoint/account/private-key identity.

A protected secret is not meant to become plaintext configuration merely because decryption fails. The safe fallback is to request the secret again.

## Session-only secrets

Quick/ad-hoc connection credentials can remain runtime-only. Passwords and key passphrases should not be written to durable application state unless the user explicitly chooses persistence and the platform protection path succeeds.

On Linux, process-local protected-secret handles distinguish session-owned and borrowed profile-owned secrets. Session-owned handles are forgotten promptly on close or failed/abandoned SFTP setup; borrowed profile secrets are not invalidated merely because one connection session ends.

On macOS, the native frontend does not receive raw durable protected-profile blobs as ordinary Swift model state. Runtime credentials remain short-lived and same-user scoped while durable profile protection is handled through the native security bridge.

## Navigation metadata

Bookmarks and profile start-directory state are local navigation metadata, not credential stores. Remote bookmark/start-directory activation is account/session bound before it becomes authoritative, so saved navigation state cannot silently become authority for a different server identity.

## Settings

Language, appearance, transfer preferences, recent local state and other maintained settings are stored locally. Settings recovery uses local backup/replacement behavior and does not contact an external Ghost FTP product service.

Classic Light is the fresh/fallback appearance. Selecting Dark is an explicit local preference on maintained native desktop frontends and does not load remote themes, fonts or style services.

## Transfer data

Ghost FTP necessarily reads local files selected for upload and writes files selected for download. Transfer content is sent only to/from the server selected by the user through the chosen maintained protocol.

Staging, rollback and source-snapshot files are local operational state. They are not uploaded to a Ghost FTP product service. Incomplete or cancelled staged downloads must not be promoted to a final user-visible object merely to simplify cleanup.

Android uses user-authorized Storage Access Framework destinations rather than hidden application-wide filesystem authority. macOS uses native file-selection/security primitives around the shared transfer engine.

## GitHub Release and Packages privacy

Official public release artifacts are built in GitHub Actions from repository source. The current public release allow-list contains only Windows/Linux binaries/packages plus generated release verification files: **14 platform artifacts / 17 public files**.

The current GitHub Package (`ghcr.io/bren-wp/ghost-ftp:0.0.5`) is built from the verified release directory only. The OCI bundle does not intentionally contain saved profiles, user files, local application data, signing private keys or CI secrets. Distribution-bundle creation does not turn GHCR into a Ghost FTP runtime backend.

The Android development APK and macOS development app are independently validated development artifacts and are not silently inserted into the public Windows/Linux release bundle.

## Signing and notarization secrets

Production Windows Authenticode credentials exist only in protected release infrastructure. Temporary PFX material is prepared in runner-temporary storage for signing and is removed after use. Official Windows publication fails closed if the trusted production identity is missing or the final public executables do not verify successfully.

macOS production signing/notarization similarly depends on external protected Developer ID and Apple notarization credentials. Those credentials are not stored in repository source and successful development-app CI must not be represented as proof that production notarization occurred.

Private signing/notarization material must never be committed to the repository or included in public release/package files.

## Documentation and screenshots

Authentic UI evidence is captured from real Windows, Linux and Android runtime surfaces by the dedicated read-only CI workflow. The workflow must not commit or push screenshot evidence back into the source branch it is validating.

The current exact-head cross-platform evidence bundle contains 15 runtime images: five Windows, three Linux and seven Android. `scripts/assemble_ui_evidence.py` verifies source SHA, workflow-run identity, expected filenames, byte counts and SHA-256 values before the bundle is accepted.

macOS has a separate native development build/validation workflow. Its development evidence is not silently added to the 15-image bundle and is not represented as public notarization evidence.

Screenshots and fixtures must contain only synthetic/non-sensitive values and must not expose real customer hosts, usernames, credentials or private local paths. Mockups or generated approximations are not substitutes for authentic runtime evidence.

Documentation media is repository-local. The active README/documentation surface does not intentionally embed **remote badge images**, **tracking pixels**, analytics images, **remote icon resources**, **remote webfonts** or other externally hosted media that would cause a network request merely because documentation is rendered. Ordinary text hyperlinks may still point to the official product, GitHub release/package pages and other documented destinations; they are not fetched by Ghost FTP at runtime.

The canonical documentation logo is `build/icon.png`. The maintained checked-in visual set includes `docs/images/ghost-ftp-main-workspace.png`, `docs/images/ghost-ftp-site-manager.png`, `docs/images/ghost-ftp-settings.png` and `docs/images/ghost-ftp-about.png`; exact-head runtime evidence is additionally published as immutable workflow artifacts rather than self-committed source changes.

## Logs and support

Ghost FTP aims to make operational logs useful without exposing credentials. Users should not paste real passwords, private keys, passphrases, production signing material or confidential server content into public support requests.

## Third-party servers and platform tools

A server chosen by the user can observe protocol traffic necessary for that connection and is governed by the server operator's own policy. System transport tools invoked by Ghost FTP operate under the local operating system and their own implementation behavior.

Build/release infrastructure may contact explicitly configured package, signing, timestamp or notarization services required to produce and verify artifacts. That release-engineering traffic is distinct from application telemetry and does not imply a Ghost FTP runtime cloud service.

## No sale of user data

Ghost FTP contains no advertising data broker integration and no product backend designed to sell application usage, profile or browsing data.
