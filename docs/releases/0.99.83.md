# Ghost FTP by Brendigo — 0.99.83 Preview

**Status:** development candidate; not published. **Previous public release:** [v0.99.82](https://github.com/bren-wp/Ghost-FTP/releases/tag/v0.99.82), published 23 November 2026. **Date:** 24 November 2026.

## Sites and connection workflow

- Connected filter reflects real session profile identifiers, and Open session focuses a live connection instead of opening a duplicate.
- Clear search, reset filters, result counts and editable site names make saved-site management faster.
- Natural sorting, consistent category counts and finite last-used timestamps are shared read-only selectors. Credentials are excluded from search.
- A synchronous action guard prevents overlapping Site Manager profile mutations. Password visibility is scoped to the displayed draft; switching sites clears visibility and metadata editing. Deletion rechecks live sessions before proceeding.
- Responsive header and search, keyboard focus outlines, accessible icon controls and sort-direction labels improve the existing branded interface.
- Regression checks cover selector behavior, privacy, invalid dates, connected filtering, and wiring.

## Follow-up audit and CI repair

- P1 (Agent config staging): a failed exclusive open previously entered the generic cleanup path and could unlink a staging file not owned by that writer. Open before cleanup ownership begins; close the owned handle before rename. Regression tests preserve existing configuration and foreign staging bytes and verify a later save succeeds.
- P2 (Sites): selected and draft profile IDs must match before rendering connection details or revealing a password. Prevent stale-draft saves and editing fields during a native mutation.
- P2 (Linux matrix): update the source contract to verify the extracted production selector and its real row wiring rather than requiring inline filtering in the dialog. Existing keyboard, deletion, native visual and protocol checks remain intact.

The Agent quota, admission lock and per-controller cap were already present; no duplicate fix is claimed. Native GUI acceptance and production signing remain separate gates.

## Agent configuration validation

- P1 (availability / configuration integrity): enforce the 1 MiB input limit on actual reads, not only the pre-read metadata. Reject non-regular opened files and distinguish missing paths from inspection failures. A dangling symlink is no longer treated as a missing configuration.
- Validate the existing 128-peer and 1 MiB limits before staging a new configuration so an invalid save cannot replace a previously readable configuration.
- Added regressions for oversized input, rejected saves preserving original bytes, and dangling symlinks on Unix. Source change: [49169d0](https://github.com/bren-wp/Ghost-FTP/commit/49169d0f7dc7ecbd2ea2341cbc83df45938abe77). Exact-head CI and native acceptance are pending. ## Download parent lifetime and Agent integration

- DownloadParentGuard keeps an open directory handle from worker admission across retries, completion and cleanup. Linux compares device/inode; Windows compares volume serial/file index from open directory handles. ## Recovery state machine and destination reservations (phase 2)

- Forward-only SQLite migration v10 adds persisted phases prepared, backup_saved, promoted, rollback_pending, rolled_back and cleanup_pending. Existing v9 records retain legacy_unknown; they are not treated as new transactions. Compare-and-set transitions require the expected prior phase and an allowed edge. Intent deletion requires cleanup_pending. Rollback completion stays recorded for review rather than authorizing an unverified stage cleanup.
- Linux and Windows native backup transactions persist phase transitions around backup, promotion, rollback and backup deletion. If publication succeeds but subsequent phase persistence fails, the backup and intent are retained. If persistence fails before publication, the operation stops and leaves recovery evidence. Phases describe the last recorded event, not an authoritative current filesystem snapshot: a process can stop between filesystem mutation and its database update.
- A unique SQLite destination reservation key derived from the pinned directory identity and target basename prevents conflicting journal insertions. Normal and Delta promotion reject already-known pending destination keys. Windows key case folding is conservative; aliases and filesystem-specific equivalence are not fully resolved. Preflight checks alone do not serialize every possible concurrent operation; no claim of complete destination locking.

## Authenticated content and recovery phase chain

- Recovery schema 2 binds full SHA-256 digests of the original and stage to the authenticated transfer intent, native file identities and sizes. A backup made by renaming the original is checked against the original digest during reconciliation. Hashing uses positional, bounded-buffer reads. Linux prefers the retained verified writer; a write-only writer requires a directory-relative read handle verified against its identity. Windows uses native relative opening and an object-bound ReOpenFile read handle. No sampled digest is accepted.
- Startup reconciliation rejects missing content evidence or phase chains and mismatching reservations before inspecting files. Its total estimated content-read budget is 64 MiB; larger records are left for manual review, not treated as verified. The existing advisory recovery decisions do not authorize mutation.
- Each authenticated phase carries a sequence and the preceding tag, linked to the immutable intent tag and authenticated with AES-256-GCM. SQLite updates phase and envelope in one compare-and-set statement that also matches the prior payload and destination reservation. Signed transactions do not silently downgrade if their vault key becomes unavailable. Transactions that began without an accessible vault remain unsigned/manual-only on restart.
- Regression coverage added for equal-length stage and backup changes, malformed or reordered phase chains, cross-transaction reuse and stale SQL envelope/reservation updates. - Limits: full-database replay of a valid prefix with the matching vault key is not prevented. Timestamp checks do not provide a locked snapshot or proof against a concurrent writer. ## Independent recovery anchor and pre-mutation verification

- An AES-256-GCM authenticated commitment to the exact serialized phase envelope is stored in a distinct OS vault service per transaction key ID. The active anchor is written and read back before the SQLite phase CAS. A stale envelope, missing anchor, unavailable vault or interrupted cross-store update cannot authorize reconciliation. A terminal commitment is stored before deleting a completed SQL row; the anchor is removed only after key deletion succeeds.
- The live Windows and Linux journal-backed rollback and backup cleanup paths recheck the anchor, exact SQL row, pinned parent identity and full backup digest; cleanup also checks the published file digest. Unsigned transactions may publish, but cannot automatically restore or discard their backups. This can leave a destination reserved until manual review; a recovery UI is still needed.
- The pure anchor regression rejects old envelopes, a different transaction and terminal replay. SQL tests exercise stale-state checks. Existing source-level audit contracts are updated to require the new native handle access, phase checks and anchors rather than obsolete call signatures. Rust formatting corrections follow the actual failed quality job.
- Limits: no atomic OS-vault/SQLite commit, no global vault index detecting deleted SQL rows or new transactions after database rollback, no protection from restoring both stores or privileged vault tampering, no complete filesystem locking or same-directory TOCTOU solution. Non-journal and Agent Delta paths are not covered by these new gates. Native vault failure injection, crash/restart tests, compilation and exact-head CI remain required.

## Global authenticated recovery index and process coordination

- A compact AES-256-GCM authenticated index in the persistent OS vault is scoped to the canonical app data directory. Its independent key is stored under a separate service. Each entry commits to the exact transaction ID, phase, destination reservation and signed SQLite envelope via SHA-256. Generation increments are authenticated. Recovery credentials use strict persistent reads without Linux legacy keyutils fallback.
- Under a native exclusive file lock, startup compares the index with SQLite and counts missing, unindexed and divergent entries. Any mismatch or unavailable vault defers filesystem inspection. Promotion and Agent Delta destination preflight also check the index and retain the lock through the native commit worker, including async cancellation. Delta does not yet journal its own atomic replacement.
- New journal transactions commit the index first, the per-transaction anchor second and the SQL row last. A phase transition uses the same order and exact SQL CAS. Completion retires the transaction anchor, deletes the SQL row, updates the index, then removes per-transaction credentials. Interrupted writes are recognized as inconsistencies; no unverified data is reconstructed or deleted.
- The index deliberately limits active entries to eight to fit the conservative Windows credential size budget. Overflow, uninitialized index with existing legacy rows, missing key/index half, locked vault and process-lock contention fail closed. All DB-backed download publication may be blocked until the vault or inconsistent ledger is resolved. This is a change in availability behavior; manual recovery tooling and safe legacy migration are still required.
- Added regression tests for index mismatch categories, malformed and tampered envelopes, cross-scope reuse, lock contention and release after forcibly killing a real child process. Native execution is still pending. The existing backup collision test distinguishes unavailable-vault refusal from actual journal-backed collision coverage.
- Scope limits: trusted persistent vault and canonical app data directory, cooperative processes on supported local filesystems, no simultaneous rollback of vault and SQL, no protection from a privileged process replacing the lock path or both stores. The digest index identifies inconsistencies but cannot reconstruct missing paths or complete interrupted transactions. There is no automatic destructive startup recovery. Full native test and exact-head CI are release prerequisites.

## Sharded authenticated recovery ledger and redundant records

- Schema v2 stores an authenticated root manifest with up to sixteen immutable eight-entry shards, increasing the active-record capacity from 8 to 128 (the current bounded SQLite snapshot). Content-addressed vault blobs use 720-byte chunks, a verified length marker written last, strict reads and a complete SHA-256 digest. The root is published only after the record and referenced shards are staged. Existing v1 indexes migrate on a write only after every SQL record and its per-transaction anchor match; divergent legacy records require review.
- Full redundant metadata (transaction ID, signed phase envelope and reservation) is retained outside SQLite. Startup reconciliation and mismatched promotion preflight can restore an absent SQL row without overwriting an existing ID or destination, or advance an exact immediately preceding signed phase using the existing CAS. A prepared record whose anchor was not yet written may establish that anchor under the trusted manifest; a noninitial phase may only advance from its exact authenticated predecessor. A terminal anchor permits retirement of the matching cleanup-pending SQL row and index entry; never resurrect a terminal row.
- Unindexed rows, malformed chunks, missing record evidence, unrelated or more-than-one-step stale phases, unknown anchors and conflicting reservations fail closed. This repairs metadata only; no automatic file rollback, deletion or publication is performed. Per-file inspection remains separately bounded. The root and vault are the trust boundary, not a separate physical backup; simultaneous rollback of both stores is not prevented.
- Regression tests added for 128-entry shard round trips, duplicate shards, root size, anchor transition recovery, missing-anchor refusal and non-overwriting SQL restore. Tests do not yet demonstrate native vault durability, complete fault injection at each boundary, or full process-crash filesystem recovery. Immutable obsolete blobs and retired credentials are retained pending a verified garbage collector; storage usage and native performance must be tested. The 128-record ceiling remains intentional, not unlimited capacity.
- Prior Windows rustfmt failures were corrected using the actual CI diff; all source-level audit gates remain enabled. Exact-head Rust compilation, Windows/Linux native tests and release gates remain pending.

## Verified recovery garbage collection and fault injection

- An authenticated bounded candidate queue (four pages, twelve blob candidates per page) registers immutable blob ownership and exact length before staging each object. Previous root references are registered before replacement. Under the interprocess lock the collector reloads the current authenticated root, checks SQL and per-transaction anchors, validates reachable objects and removes only registered unreachable blobs. Complete blobs are digest-verified before removing their length marker; the authenticated candidate then permits idempotent chunk cleanup after interruption. Unknown unregistered credentials are not swept.
- A separate authenticated queue (32 key IDs) records per-transaction keys before creation and again before terminal retirement. Only keys absent from the verified active ledger are removed, key first and anchor second, with strict persistent-vault readback. A crash after key creation or between key and anchor removal can be retried. Existing historical unregistered blobs/keys from earlier builds are intentionally not deleted.
- A test-only file-backed credential adapter supports process-kill fault injection with real SQLite, recovery locking and native Linux/Windows promotion calls. It is not a production configuration option. The matrix contains 30 selected durable boundaries, including key registration/creation, partial blob staging, root publication, prepared/advanced phase commits, native backup rename/publication/deletion, terminal retirement and partial GC. Restart checks include idempotent metadata reconciliation, active-object retention, actual absence of unreachable registered chunks/keys, and preservation of unrelated/user data except deliberately completed backup deletion.
- Separate regression checks reject a tampered GC page and preserve an unrelated vault entry. Prior CI-reported formatting differences were corrected; the security audit now requires the new collector and fault-test wiring. No test or release gate was disabled.
- Limits: test-only vault is not native Credential Manager/Secret Service, so physical vault durability, power-loss and arbitrary intra-write crashes remain unverified. The fault matrix is not exhaustive (initial index bootstrap, rollback branch, legacy migration and native vault failures still need dedicated tests). Large live-ledger verification and repeated vault operations require native performance testing. Existing unregistered objects are preserved; the queues bound pending registered garbage, not total historical vault size. Filesystem TOCTOU, Agent Delta integration and actual automated file recovery remain separate tasks. Exact-head CI and native execution are required before release.

## Native vault durability, rollback crash matrix and reduced write amplification

- Native test mode uses the actual production credential adapter (Windows Credential Manager or Linux Secret Service), never the file-backed test vault. Each test has an isolated UUID-named data directory, unique scoped accounts and a durable test-only ownership registry for cleanup. Explicit mandatory native CI steps run the ignored-by-default native test on both platforms; Linux starts a separate D-Bus/keyring session. An unavailable native vault is a test failure, not a skip.
- Eight native process-kill checkpoints cover transaction key creation, prepared manifest, phase SQL commit, terminal anchor, key retirement and three rollback boundaries. The isolated file-backed matrix is extended by seven rollback checkpoints (37 total). A test-only promotion failure activates the real guarded rollback path; the parent checks the authenticated phase and exact original/stage/backup namespace after restart. No runtime switch enables fault injection in production.
- Existing identical immutable chunks no longer need a duplicate readback; newly written values still require readback. Shard updates reuse unchanged authenticated shards after verifying their content, register only superseded shards for GC and stage only new shards. This reduces redundant vault calls without weakening the current root, SQL or GC verification. Each crash case reports elapsed time; measured native latency and throughput comparisons remain pending.
- This suite tests process death and cross-process persistence, not a real system reboot, disk power loss, native service crash or arbitrary interruption during OS credential writes. Actual native CI success is required before claiming durability. Test credential cleanup on a failed assertion and complete historical garbage accounting remain follow-up work. No automatic destructive startup file recovery is enabled.

## Vault service restart and filesystem durability barriers

- SQLite FULL synchronous mode is verified after configuring WAL. A private initialization sentinel is synced before first vault bootstrap; loss of both root and key in an initialized profile refuses automatic reinitialization, even if SQLite is empty. An interrupted first bootstrap or damaged sentinel needs manual review. The sentinel is a denial guard, not an authenticated anti-rollback root.
- Linux journal-backed promotion syncs original/stage data and the pinned directory before creating intent. Directory entries are synchronized after backup rename, publication, rollback and backup removal before advancing the corresponding durable phase. An uncertain sync preserves evidence. Four Linux-only process-kill checkpoints cover these barriers. Windows retains the existing file flush and handle-based namespace operations; directory/power-loss equivalence is not established.
- Linux CI restarts the disposable GNOME Secret Service daemon by killing only its verified same-session D-Bus owner, unlocks the same isolated keyring and verifies authenticated recovery metadata from a new process. Windows CI checks native cross-process persistence, not restart of Credential Manager. No host service is restarted on Windows.

This measures manifest I/O, not full transfer or filesystem recovery. Actual measurements require successful runner execution.

## VM hard reset and native end-to-end durability suite

- Windows journal-backed overwrite now flushes the same verified file object through a separately reopened write-capable handle before intent, after backup rename/rollback, after publication and before cleanup retirement. File identity is checked before and after the flush. If a write-capable reopen or flush is unavailable, the operation refuses or retains recovery evidence; read-only original files may no longer be overwritable through this protected path. File-level flush is not a documented directory or volume namespace durability guarantee; Windows power-loss behavior still requires actual verification.
- Four Windows-specific process-kill checkpoints exercise these flush boundaries. Seven previous rustfmt differences were applied from the actual Rust workspace failure log.
- A dedicated native VM guest probe prepares unique durable fixtures, runs real journal-backed promotion up to a selected checkpoint, then verifies the authenticated root and SQL after reboot without automatically altering user files.
