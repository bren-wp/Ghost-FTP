# Native credential vault migration — design and acceptance

The current Linux path uses libsecret's secret-tool with the existing attributes application=ghostftp, service, account. Legacy profile compatibility remains in credentials.rs; strict recovery calls must never fall back to volatile storage.

## Candidate architecture

Evaluate a maintained direct Secret Service binding over D-Bus or libsecret, with encrypted sessions and bounded cancellation, rather than a persistent shell helper. The lockfile already contains zbus transitively; that alone does not establish the required API, feature set or compatibility. Do not switch the production backend or add a dependency until the following acceptance is demonstrated.

- Read credentials created by the existing secret-tool path, and verify the inverse on a disposable persistent keyring.
- Preserve exact attribute identity, UTF-8 bytes, collection semantics and existing duplicate/error behavior; locked or unavailable collections must not be treated as missing.
- Distinguish missing item, locked collection, transport error, timeout, prompt cancellation and service restart. Never downgrade to legacy or session storage on strict reads.
- Preserve write and delete read-back, HMAC/digest checks, interprocess locking and the existing on-disk format. Do not cache credentials or keys across operations.
- Test GNOME Keyring and supported KWallet configurations, persistent survival across service/OS restart, existing profile and OAuth compatibility, revocation and no credential disclosure in logs.
- Compare exact-source native ABBA runs and occupancy bands, publish raw observations, and keep the subprocess implementation until equivalence and failure semantics are verified.

## Isolated direct API prototype

`tools/native-vault/direct-secret-service.c` exercises a reusable libsecret service session, exact existing attribute matching, persistent default-collection selection, strict unique-item lookup without unlocking prompts, verified writes/deletes and compatibility with secret-tool. The workflow uses disposable GNOME Keyring sessions, tests a locked collection and attempts a fresh service session with the same isolated persistent data. It compares repeated lookup latency on the same runner, using ABBA ordering and raw samples. The prototype is not linked into the production Rust application; the outer test-process deadline is not a production cancellation mechanism. KWallet and in-process reconnect/cancellation remain explicit acceptance gates.

## Rust integration candidate

The `native-vault-candidate` Cargo feature builds a native bridge for Linux test binaries only. Explicit disposable native recovery fixtures may select it; normal release builds retain secret-tool. A thread-owned service session uses a joined GCancellable deadline worker and checks the current D-Bus service owner before and after each operation. Uncertain operations invalidate the session and are never automatically replayed. Existing attributes, read-back, and recovery locks are preserved. Cancellation is cooperative, not a hard OS process kill; live blocked-provider, KWallet and restart-during-operation acceptance remain required.

## Failure and acceptance gate

The candidate bridge is built unchanged into a standalone failure harness. In a disposable GNOME Keyring D-Bus session, a verified fixture daemon is stopped, a 200 ms lookup must return failure within 2 seconds, then the daemon is resumed and the credential reread. A second blocked lookup is interrupted by terminating that same daemon, followed by a new provider process and verified readback. A passing read-only failure test does not establish safe cancellation of in-flight mutation. `tools/native-vault/kwallet-acceptance.sh` is an explicit manual provider-identity-checked CRUD acceptance harness for an unlocked dedicated KWallet test account (KF 5.97+ or compatible KF6 Secret Service); it rejects GNOME fallback. KWallet lock/restart and mutation uncertainty remain release gates. The full recovery benchmark now requests 100 observations per backend and file size using ABBA/BAAB on the same runner. Default historical benchmark remains three samples.

## Transactional mutation uncertainty

The bridge distinguishes a dispatched mutation with uncertain outcome (-2) from a pre-dispatch error. The Rust adapter invalidates its session on uncertain outcomes or failed readback; it never retries automatically. An isolated callback gate after a successful native write/delete but before final owner validation allows the test harness to terminate the provider at the acknowledgement boundary and verify durable state after restart without replay. This is not an atomic transaction across the credential store and SQLite. Mid-RPC mutation fault coverage and durable reconciliation across application restart remain mandatory before production activation.

## Persistent mutation journal candidate

The feature-gated test adapter now has a separate SQLite intent prototype: FULL synchronous commit, immutable single-slot insertion, AES-256-GCM authenticated encryption bound to a scope, external SHA-256 envelope anchor and one-shot dispatch permit. Credential values are not persisted; only encrypted commitments and identity are stored. Reopening never returns a dispatch permit. Observation classifies desired, original, conflicting or unavailable state without writing or deleting credentials. An unanchored intent blocks rather than being silently recreated. Tests cover tampering, key mismatch, duplicate insertion, application process kill with a synthetic provider, and separate native vault key/anchor readback after session reopen. This is intentionally a single-intent prototype, not a complete production transaction manager: externally trusted anchor enrollment, atomic cross-process coordination with the native provider, durable terminal-state/retention protocol, rollback protection across both stores and native mid-RPC interruption remain required. No application schema migration or production routing is changed.

## Append-only multi-operation ledger candidate

The separate feature-gated ledger stores authenticated AES-GCM events with an explicit sequence and previous envelope digest. A caller-supplied independent anchor must match the full chain before every append; SQL commit precedes anchor advance and verified readback. Any mismatch blocks subsequent work, without deleting the latest journal. An exclusive verified Linux file lock covers the ledger lifetime and live dispatch; unrelated credentials can have multiple unresolved intents, while a second intent for the same unresolved identity is refused. Dispatch is serialized, not parallel. Only a successful live mutation with desired readback can append an archive event; uncertain reconciliation is observational and cannot issue another permit. Archive means a logical marker, never deletion. The 4096-event bound fails closed without pruning. The anchor adapter in these tests is synthetic, and simultaneous rollback of both stores cannot be detected by this design. Native anchor enrollment, cross-process kill tests, secure directory/DB identity, external provider coordination and production migration remain required.

## Native anchor and immutable checkpoint export candidate

An explicitly enrolled disposable Secret Service anchor stores the sequence and digest, compares the preceding head and verifies readback. Reopening does not enroll a missing anchor. The checkpoint exports a compact authenticated projection retaining all transaction IDs and terminal/unresolved states, plus the complete original encrypted event chain into new files. Both files are fsynced, the destination directory is synced, and independent replay and checkpoint decryption must match the external head. Existing copies are never overwritten; no physical compaction, automatic deletion, source replacement, or production routing is implemented. Copy destinations in tests are separate directories, not verified independent physical media. Native anchor enrollment is fixture-only; key persistence and trust provisioning, race-resistant directory/SQLite identity, coordinated rollback resistance and crash-safe publication across all stores remain open. Two killed child processes test lock recovery, not crash consistency of all checkpoint phases.

## Multi-phase generation publication candidate

New private generation directories contain the complete encrypted chain, authenticated checkpoint and sealed manifest binding generation identity, trusted head and both file digests. Each file is synced; a no-replace hard link publishes the committed marker, followed by directory sync and full readback. Incomplete generations and all prior copies are retained. Selection is deterministic among verified copies at the exact current external head; stale generations are not live rollback candidates. Eight process-kill checkpoints exercise directory creation, file sync, verification, manifest and marker publication. SIGKILL testing does not simulate physical power loss; a marker visible after link but before directory sync may survive or disappear after power loss. This is generation rotation of full exports, not active ledger segment rotation or physical compaction. Backup root is explicit, but physical independence and mount identity are not verified. Filesystem race hardening, native-anchor crash matrix, authenticated segment switching and off-device restore acceptance remain required.

## Authenticated segment activation and recovery migration candidate

A rotation event commits the preceding head, next logical segment number, verified generation identity and publication marker digest into the authenticated global chain. The rotation event remains in the previous segment; subsequent events use the segment table. Full replay verifies physical row assignment against authenticated sequence boundaries; the old rows are never removed. SQL commit precedes external anchor advance as before: mismatches fail closed rather than silently activating an older segment. The ledger still uses one SQLite database and retains the global event limit; no physical compaction is claimed. A conservative Linux sysfs check rejects shared filesystem or underlying block devices and unknown/virtual/layered topology. It is not proof of physical independence, especially on virtual machines, and no real separate hardware was tested. Migration copies a verified current generation without overwriting and reconstructs the marker only after checking the payload. Restore reconstructs encrypted ledger rows in a new empty directory, checks the same externally supplied key and trusted anchor, and never writes credentials. The regression uses separate directories on one machine, explicitly exercising the same-device refusal and internal rotation; no replacement-machine key/anchor recovery or real physical power-loss test is claimed. Native anchor/key enrollment and independently trusted media identity remain production gates.

## Portable recovery key candidate

The portable export wraps the 256-bit ledger key using AES-256-GCM with a separate randomly generated 256-bit wrapping key (not a human password), fresh nonce and domain-separated AAD. The encrypted payload binds format, scope, trusted head, exact generation ID and publication digest. An independently trusted receipt binds scope, head and package digest; it must be kept separately from the exported media and must represent the latest authorized recovery state. The package cannot establish its own freshness: rollback of both receipt and package remains possible. The restore adapter is read-only, rejects anchor advancement, checks the exact generation and reconstructs a new empty database without issuing dispatch permits, enrolling a native anchor or modifying credentials. The test uses synthetic key files to simulate separate transport and a new process, not a second machine. Byte-buffer clearing is best-effort, not guaranteed zeroization of all copies. Secure user key custody, authenticated receipt delivery, trust re-enrollment on replacement hardware, native vault credential recovery and full cross-machine disaster recovery remain required. No production activation.
